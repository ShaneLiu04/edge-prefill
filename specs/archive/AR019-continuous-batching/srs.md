# [AR019] 需求设计说明书

| 字段 | 内容 |
|------|------|
| AR 编号 | AR019 |
| AR 主题 | 连续批（continuous batching / iteration-level scheduling）：解码槽位随时准入与退出，提前完成的用例不再陪跑，后来的用例不再等满一批 |
| 关联 SR | 承接 AR017（锁步批解码）、AR018（GPU 预填充 ‖ CPU 解码 + KV 交接）；对标 vLLM 的 iteration-level scheduling / Orca 的 selective batching |
| 日期 | 2026-10-31 |
| 状态 | Draft |

## 1. 背景与目标

### 1.1 两个已入库的批处理方案各有一半问题

| 方案 | 吞吐 | 单例 E2E | 问题 |
|---|---:|---:|---|
| AR017 锁步批（K=4） | 100.4 s / 16 用例 | 3578 ms | 一批里**所有人陪跑到最慢的那个**：E2E 被算成 `ttft + 整批墙钟`，早完成的用例白等 |
| AR018 预填充/解码分离 | **38.0 s**（2.65× AR017） | 12056 ms（3.2× 差） | 解码槽位**按批发放**：一个用例平均等 1.5 批（`queue_wait_ms` 7.0–7.5 s，占 E2E 55–60%） |

两者都在"批"的粒度上做静态划分：批一旦成形，成员就固定到批结束。而真实负载里
每个用例的解码长度不同、到达时间不同，静态批必然产生"陪跑"（拖慢延迟）或"等批"（浪费吞吐）。

### 1.2 目标

把"批"从**静态分组**变成**每个解码步的调度决定**（vLLM / Orca 的核心思想）：

- 每个解码步只包含**当前活跃**的序列；
- 某序列 EOS/达上限 → 当场退出，槽位立刻让给下一个已预填充好的用例；
- 用例的预填充一完成就可准入，不必等 K 个凑齐；
- 每个用例的 E2E = 自己的预填充 + 自己的解码步，不背别人的账。

### 1.3 验收标准（也是组合是否升级的判据）

| 编号 | 标准 | 度量 |
|---|---|---|
| AC-1 | 质量不变 | 逐例 f1 与串行相同；生成哈希允许 AR014 浮点口径（≤5% 臂-用例差 1 token） |
| AC-2 | 吞吐不劣于 AR018 | 墙钟 ≤ 1.05× AR018 pipeline |
| AC-3 | **单例延迟回到 AR017 水平** | 单例 E2E 中位数 ≤ 1.2× AR017 锁步批 |
| AC-4 | 不陪跑 | 早完成用例的 E2E < 同批最慢用例的 E2E（审计列可证） |
| AC-5 | 槽位真的复用 | 每批的准入次数 > 槽位数（16 用例 / K=4 时 ≥ 13 次准入） |
| AC-6 | 无静默降级 | 串行回退、准入失败、KV 交接失败都写审计与告警 |

只有 AC-1..AC-6 全部满足，AR019 才进入默认组合；否则按 AGENTS.md 回退到
AR013+AR016+AR017(K=2)，并把负结果写进 portfolio。

## 2. 需求范围

### 2.1 范围内（FR）

- **FR-1 连续调度器**：解码上下文维护 K 个槽位；调度循环
  `准入（ready 队列 + 空槽）→ 一步 decode（仅活跃序列）→ 退休（EOS/上限）→ 释放槽位`。
  与 AR018 的预填充 worker 组合时，准入直接消费 worker 的就绪结果（含 KV 交接）。
- **FR-2 准入策略**：就绪即准入；槽位满时按到达顺序排队；至少保留 1 个空闲槽位给
  下一个完成预填充的用例（避免队头阻塞）。
- **FR-3 逐例记账**：`e2e = 自身预填充 + 自身解码`（不再用整批墙钟）；
  审计 `continuous`、`slot`、`admit_step`、`own_steps`、`peer_steps`（有同批伙伴的步数）。
- **FR-4 失败路径**：预填充失败/交接失败 → 该用例标记失败并释放槽位，其余用例继续；
  连续模式下 KV 交接失败不得污染其他槽位。
- **FR-5 闸门与注入**：`ar019_report.py` 至少 6 项检查（质量、稳定性、吞吐 vs AR018、
  延迟 vs AR017、不陪跑、槽位复用）+ 注入 `lockstep-peers`（把每例 e2e 改回整批墙钟）、
  `no-reuse`（准入次数=槽位数）、`quality-drift`。
- **FR-6 组合决策**：四种组合（serial / AR017 / AR018 / AR019(+pipeline)）同会话交错测量，
  按 §1.3 判定是否升级默认组合。

### 2.2 范围外

- 不做 prefill 与 decode 在**同一前向**里的混合批（llama.cpp 的 gather 补丁是图级全局状态，
  prefill 模式会污染解码 token；这是 AR020 的课题）；
- 不做抢占（preemption）/换出到主机内存；
- 不改批大小上限（仍受 `decode_batch_ctx` 与 KV 份额约束）。

## 3. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 连续解码让每步的序列集合变化，批形状抖动 | 每步 kernel 启动开销上升 | 实测对比；必要时设"最小活跃数"避免 1 序列步进 |
| 槽位复用与 KV 状态残留 | 结果污染 | 退休时 `reset_sequence(slot)`，准入时 `set_seq_state` 前 `seq_rm`（AR018 已有） |
| 逐例 E2E 与 AR017 口径不可比 | 误判延迟改善 | 同时保留 `batch_wall_ms` 与 `own_steps`，报告给出两套口径 |
| 主机噪声 | 结论不稳 | 同会话交错、每臂取最小、逐例中位数（AR017/18 口径） |
