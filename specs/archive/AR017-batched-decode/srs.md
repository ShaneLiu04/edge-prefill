## 1. 背景与目标

### 1.1 量化现状（来自已入库的 ar016 结果，CPU 12 线程）

| 数据集 | TTFT | E2E | 其中生成 | 占比 | 准入 token |
|---|---:|---:|---:|---:|---:|
| 4K | 2578 ms | 12520 ms | 9964 ms | 80% | 642 |
| 8K | 4511 ms | 19533 ms | 15037 ms | 77% | 1117 |
| 32K | 4758 ms | 20559 ms | 15694 ms | 76% | 1166 |
| 64K | 4339 ms | 17780 ms | 13452 ms | 76% | 1163 |
| 多针 | 4692 ms | 19456 ms | 14764 ms | 76% | 1117 |
| 多事实 | 1877 ms | 8468 ms | 6579 ms | 78% | 521 |
| 多事实 hard | 1806 ms | 8661 ms | 6829 ms | 79% | 511 |

即：**AR001–AR016 把首 token 压到 1.8–4.8 s，但用户感知的 E2E 有 76–80% 在解码段**，
而每个用例都串行地"一次只解一个 token"。48 token × 142–208 ms/token。

解码的单 token 成本是**权重读取**（1.5B Q4 ≈ 0.95 GB）而非算力：实测 142 ms/token ≈ 6.7 GB/s，
远低于本机内存带宽。**同一份权重在同一时刻可以服务多个序列**——这正是连续批处理的前提。

### 1.2 目标

在**不改变任何单序列输出**的前提下，让一次解码前向服务 K 个序列：

- 吞吐：N 个用例的总墙钟时间从 `N × T_serial` 降到约 `ceil(N/K) × T_step(K)`；
- 单例延迟：批内单例的 E2E 不劣于串行（批步进按最慢序列表推进，最多 `max_new_tokens` 步）；
- 质量：逐例答案与串行路径相同（允许 AR014 同口径的末位浮点翻转为上界，均值不得下降）；
- 设备：CPU 与 GPU 都要测；解码是带宽受限，两者都应受益，报告要给出各自的倍率。

## 2. 需求范围

**In Scope：**
- `LlamaBackend`：多序列上下文（`n_seq_max`）、`decode_batch(tokens, seq_ids, positions, logits)`、
  `reset_sequence(seq_id)`、`prefill(..., seq_id)`
- `BenchmarkRunner`：`decode_batch_size K`（1 = 关闭，保持 AR016 行为）；延迟生成队列：
  每个用例照常做准入/prefill（**各自在自己的 seq 上**），把「下一个 token + logits」入队，
  队列满 K 或数据跑完时做一次锁步批解码，直到所有序列结束或达 `max_new_tokens`
- KV 容量：批内所有序列的 KV 必须同时驻留，`n_ctx >= Σ span + headroom`；不足以容纳 K 个时
  **按实际可容纳的序列数降批**，并写入审计列（不得静默丢用例）
- 审计列：`batch_size`、`batch_wid`、`batch_steps`、`seq_id`、`decode_ms_per_token`
- `ar017_matrix.py` / `ar017_report.py`（质量等价 + 吞吐 + 单例延迟 + 降批行为 + 两种注入）
- 文档、`repro.sh ar017`、README、research §19、architecture、portfolio、组件详设

**Out of Scope：**
- 跨请求共享前缀 KV（AR016 已论证收益 <15%）
- 抢占/换出（preemption）与分页 KV：序列数受 KV 容量约束，超限即降批
- 修改 llama.cpp 上游（只用公开的 `llama_batch` 多 seq_id 能力）
- 改变准入/预算（批处理只影响"怎么解码"，不影响"算什么"）

## 3. 功能需求

### 3.1 FR-1 多序列解码原语

- `decode_batch` 接受长度相同的 `tokens`/`seq_ids`/`positions`，构造一个 `llama_batch`：
  每个 token 一个 `seq_id`、独立 `pos`、`logits=1`；一次 `llama_decode`；按输入顺序取回每 token 的 logits。
- 严格要求：`seq_ids` 互不相同（同一批内不让两个 token 落同一序列）、位置单调、`n_seq_max` 足够。
  违反 → `InvalidArgument`，不得静默截断。
- 真机等价测试：同一组 token 序列，批解码得到的 logits 与逐序列解码最大绝对差 < 1e-3
  （不同 tiling 的浮点差异），且贪心 argmax 逐 token 相同。

### 3.2 FR-2 批解码调度

- `K = 1` 时走原有串行路径，逐位不变（回归基线）。
- `K > 1` 时：按用例顺序收集，批内每个用例在自己的 `seq_id` 上完成 prefill（保留 AR002/AR012/AR013
  的准入与 gather 路径，gather 只在 prefill 期间启用，解码前必须复位）。
- 锁步：每步对"仍活跃"的序列各解一个 token；某序列命中 EOS 或达到 `max_new_tokens` 即退出该批的后续步
  （退出后不再占 batch 位置）。
- 队列在下列任一条件触发冲刷：攒满 K；或调用方显式 flush（数据集结束）。

### 3.3 FR-3 质量与延迟口径

- 质量：逐例 f1 与串行路径相同；允许 ≤5% 的用例出现浮点翻转，但批均值不得低于串行均值（与 AR014 同口径）。
- 延迟必须同时报告两种口径，不得混用：
  - **单例延迟**：批内某用例从提交到结束的墙钟（批内会与同批其它序列共享步进）；
  - **吞吐**：处理 N 个用例的总墙钟 `T_batch` vs 串行 `T_serial`，以及 `T_serial / T_batch` 倍率。
- TTFT 不受影响（prefill 仍是逐用例串行），报告中必须显式写明"这是 E2E/吞吐收益，不是 TTFT 收益"。

### 3.4 FR-4 KV 容量与降批

- 批前按 `K × (span + max_new_tokens + 8)` 预分配 `n_ctx`（不超过模型训练上下文）；
  若不足，按可容纳序列数降批（`K_eff = floor((n_ctx_train - headroom) / (span + gen))`），
  并把 `K`、`K_eff`、原因写入审计列与日志。
- 降批不得丢用例：降批后的剩余用例进入下一批。

### 3.5 FR-5 组合与回退

- 与 AR016 组合：批解码不与 SLA 冲突（SLA 只改预算）；批矩阵必须使用 AR016 的 probe 计划。
- 与 AR014 组合：多轮数据集在同一批里可能出现同一会话的相邻轮次（有依赖），必须**按会话依赖串行化**
  （同一 session 的轮次不得同批），否则会改变语义。这是硬约束。
- 若综合结果（质量 + 单例延迟 + 吞吐）不优于 AR016 组合，则默认关闭（`decode_batch_size=1`）并记录负结果。

### 3.6 FR-6 闸门与注入

闸门（`ar017_report.py`）：
1. 质量等价（逐例；均值不降）；
2. 吞吐：`T_serial / T_batch >= 1.5`（K=4 时应更高）；
3. 单例延迟：批内单例 E2E ≤ 串行单例 E2E × 1.35（批不显著拖慢单例）；
4. 输出确定性：同配置重复运行，逐例答案文本一致；
5. 降批审计：`K_eff <= K` 且用例数不丢。

注入：①`shared-seq`（把两个用例放进同一个 seq）必须 FAIL（KV 会互相污染）；
②`quality-drift`（人为改动批内某序列的 logits）必须 FAIL。

## 4. 非功能需求

| 项 | 要求 |
|---|---|
| 数值 | 批解码与逐序列解码的贪心输出逐 token 相同（真机测试），差异只允许出现在末位 logits |
| 错误处理 | 容量不足 → 降批 + 审计；序列 id 冲突 → `InvalidArgument`；不得回退到"静默串行"而不记录 |
| 复现 | 矩阵脚本记录 K、K_eff、线程、设备、模型 hash；`repro.sh ar017` 一条命令跑完并过闸门 |
| 性能 | K=1 时与 AR016 完全一致（零回归） |
| 依赖 | 只用 llama.cpp 公开 API（`llama_batch` 的 `seq_id` 数组），不改上游 |

## 5. 约束与假设

- 单序列贪心解码；批内不同序列步数不同，按最慢推进，已结束的序列退出。
- 同一会话的轮次有数据依赖，不得同批（AR014）。
- 本机 GPU 处于低 P-state（AR016 已记录），批解码是带宽受益，仍应体现倍率；若不体现，如实记录。

## 6. 组合分析（为什么是这个 AR）

| 候选 | 判断 |
|---|---|
| **批解码（本 AR）** | E2E 的 76–80% 在解码；单 token 成本是权重读取，同批 K 个序列共享一次读取；与已有 AR 无收益通道冲突 |
| 证据重排（证据靠近问题） | 零 FLOPs 的质量假设，但会改 KV 布局与 gather 映射，先做 AR017；若批解码收益成立，重排留待后续单独验证 |
| 跨问题共享头部 KV 池 | AR016 已量化：结构块仅占 8–10%，收益 <15%，不做 |
| KV 量化（Q8_0/Q4_0） | 只降 KV 读取；本场景 KV 只有几 MB，权重才是瓶颈，收益小 |
| 只调解码线程数 | 已在 AR016 的 plan 里；收益 1.3× 量级，远小于批处理的 K× |

组合关系：AR012/AR013 决定每个序列的长度（批内 KV 占用），AR016 决定线程/设备，AR014 施加
"同会话串行"约束，AR015 的快照在批内仍然逐用例生效（命中即跳过 prefill，不影响解码批）。

## 7. 术语说明

- **批解码（batched decode）**：一次 `llama_decode` 同时推进多个序列各一个 token。
- **锁步（lockstep）**：批内每步为所有活跃序列各解一个 token。
- **K_eff**：受 KV 容量限制后实际可同批的序列数。
- **单例延迟 / 吞吐**：见 FR-3，两者不得混用。
