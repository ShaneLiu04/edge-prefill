# AR019 连续批（iteration-level scheduling）— 实验报告

日期：2026-10-31
设备：GPU（RTX 5000，29/29 层，P8）预填充 + CPU（12 线程）批解码（AR018 流水线）
模型：`qwen2.5-1.5b-instruct-q4_k_m.gguf`
数据：`deep/multifact8k`（16 用例），`budget=0.05`，`max_new_tokens=48`，`warmup=1/repeats=1`
方法：同会话交错，3 轮 × {K=4, K=8} × {静态批, 连续批}，每臂取最小墙钟

## 1. 结论（先给判断）

**连续批没有让组合变好，按"组合不劣"原则不设为默认。**

| K | 静态批墙钟 | 连续批墙钟 | 吞吐 | 单例延迟（e2e_wall） |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 32.0 s | 31.1 s | **1.03×** | 13.5 s → 17.4 s（**差 29%**） |
| 8 | 34.2 s | 31.7 s | **1.08×** | 23.3 s → 19.3 s（好 17%） |

质量与答案：两种模式 16/16 用例 `generated_hash` 完全相同，f1 相同（0.975）。

即：K=8 时吞吐 +8%、延迟 -17%；K=4 时吞吐 +3% 但延迟差 29%。噪声级别（本机单点可差 2–3×）
之内，且**没有达到**"默认组合必须更优"的标准。

## 2. 为什么只能拿到个位数百分比（根因分析）

这台机器的流水线是**预填充受限**的：16 个用例的 GPU 稀疏预填充串行执行，
1.9 s/用例 → 30 s 下限；而解码总工作量只有 8–14 s（AR018 实测）。
解码调度能优化的上限就是"把 8–14 s 的解码藏进 30 s 的预填充里"，
而静态批本来就已经藏掉了大部分——所以连续批只剩下尾部与批边界的收益（3–8%）。

连续批真正能兑现的场景是"解码占主导 + 用例长度差异大"（vLLM 的典型负载），
这在端侧单用户、固定 48 token 生成长度的负载里并不成立。**这是本 AR 的主要收获**：
它把瓶颈定位从"调度"钉死到"预填充吞吐"，直接指向下一个 AR（并行预填充）。

## 3. 实现（保留为可选开关）

- `continuous_batch=1`：解码上下文维护 K 个槽位；每个调度步只解码活跃序列；
  用例 EOS/达上限即退休并释放槽位，供下一个已预填充的用例立即使用；
- 与 AR018 组合时，准入消费预填充 worker 的就绪结果（非阻塞 `pipe_try`），
  解码永不为等预填充而停摆；
- 单上下文模式（无流水线）下，槽位在入队时分配、退休时归还；
- 审计列：`continuous` / `slot` / `admit_step` / `own_steps` / `peer_steps` / `e2e_wall_ms`。

### 3.1 新增的公平口径 `e2e_wall_ms`

发现 AR017 的 `e2e_ms = ttft + 整批墙钟` **不含**"等同伴预填充"的时间，因此
锁步批看起来比实际更好、也无法与连续批比较。新增 `e2e_wall_ms = 用例进入运行器到最后一个 token`，
对所有臂同一口径（`e2e_ms` 保留原定义，不推翻历史数据）。按新口径：

| 臂（16 用例） | e2e_wall 中位 |
| --- | ---: |
| AR017 锁步（K=4） | 11.6 s |
| AR018 流水线（K=4） | 14.1 s |
| AR019 连续（K=4） | 12.8 s |
| AR019 连续（K=8） | 19.3 s |
| AR018 流水线（K=8） | 22.5 s |

## 4. 闸门（5 项）与注入

| 检查 | 结果 |
| --- | --- |
| answers-identical | PASS（与静态批逐例相同） |
| quality | PASS（f1 相同） |
| throughput | PASS（K=4 1.03×、K=8 1.08×，阈值 0.98× 防回归） |
| iteration-level-scheduling | PASS（16 次准入 / 4 槽 = 4.0×；own=37 步；peers=4） |
| latency-recorded | PASS（信息项：K=4 0.85×、K=8 0.80× 静态） |

注入：`quality-drift`（只污染连续臂）、`lockstep-peers`（伪造成单序列解码）、`slow`（把连续批墙钟翻倍）→ 三种均 FAIL。

## 5. 组合决策（回退）

按 AGENTS.md 与 AR 验收标准，AR019 未满足"吞吐不劣化且延迟回到 AR017 水平"：

- 默认组合保持 **AR013 + AR016 + AR017（K=2）**；
- AR018 仍是可选吞吐模式，AR019 作为 AR018 之上的可选**调度**开关（默认 0）；
- 负结果与根因（预填充受限）写入 portfolio 与 research §21，作为下一 AR 的输入。

## 6. 实施中修掉的问题（记录，便于复现）

1. 连续模式下"槽位在入队时已占用"，而准入又要求空槽 → 调度器空转（实测卡死），
   已改为按作业判断；
2. 每次提交就 pump 一次，会让每个新用例只得到一步"独跑"（`peers=1`），
   已改为提交全部后再连续解码；
3. 尾部未 drain、RAII join、非阻塞准入等（AR018 遗留）在本 AR 一并确认。
